# React Native + WebView 移动端方案

## 背景

当前项目已经具备 React Web 游戏大厅和 J2ME/MRP 运行时。移动端首版计划采用 React Native（RN）作为应用宿主，通过 WebView 复用现有 Web 大厅和游戏运行时，减少重复实现，并为后续原生化保留边界。

## 目标

- 使用 RN 负责移动端应用壳、导航、生命周期和系统能力。
- 使用 WebView 承载现有 Web 游戏大厅及运行时。
- 建立有版本约定的 RN/WebView 双向通信协议。
- 在 Android 和 iOS 上打通游戏启动、返回、横竖屏、音频、网络和存档流程。
- 保持 Web 端独立部署和使用，不让移动端方案反向依赖移动端能力。

## 非目标

- 首版不重写现有 Web 游戏大厅或运行时。
- 首版不把所有页面迁移为 RN 原生页面。
- 首版不提前绑定账号、支付、推送等尚未确定的业务能力。

## 架构

```text
┌──────────────────────────────┐
│ React Native                  │
│ 应用启动 / 导航 / 生命周期     │
│ 权限 / 文件 / 更新 / 系统能力  │
└──────────────┬───────────────┘
               │ 双向消息桥接
┌──────────────▼───────────────┐
│ WebView                       │
│ React 游戏大厅                │
│ J2ME / MRP Web 运行时         │
└──────────────────────────────┘
```

### RN 宿主职责

- 创建和销毁 WebView，处理前后台切换及页面恢复。
- 负责原生导航、返回手势、状态栏、横竖屏和权限请求。
- 为 WebView 提供文件、缓存、网络状态和系统设置等能力。
- 统一处理移动端加载失败、版本更新和错误恢复。

### WebView 职责

- 加载现有 Web 游戏大厅和运行时。
- 负责游戏列表、游戏设置、输入处理和运行时 UI。
- 通过桥接协议请求 RN 提供的移动端能力。
- 在没有 RN 桥接时继续支持纯 Web 环境。

## 通信协议

协议使用 JSON 消息，消息至少包含 `version`、`id`、`type` 和 `payload` 字段。需要返回结果的请求使用同一个 `id` 关联响应。

```json
{
  "version": 1,
  "id": "msg-123",
  "type": "storage.get",
  "payload": { "key": "game-settings" }
}
```

首版候选消息：

| 类型 | 方向 | 用途 |
| --- | --- | --- |
| `app.ready` | WebView → RN | Web 内容完成初始化 |
| `navigation.back` | WebView → RN | 请求原生返回 |
| `storage.get` / `storage.set` | 双向 | 读取和写入移动端存档或设置 |
| `file.pick` / `file.save` | WebView → RN | 访问本地文件 |
| `network.state` | RN → WebView | 推送网络状态变化 |
| `screen.setOrientation` | WebView → RN | 请求横屏或竖屏 |
| `share.open` | WebView → RN | 调用系统分享 |

协议需要定义超时、错误码、能力探测和版本兼容规则。WebView 页面必须能识别未提供的能力，并回退到 Web 平台行为。

## 资源加载

首版同时保留本地构建和远程入口的实现可能性：

- 开发和离线验证优先使用本地 Web 构建产物。
- 线上方案根据包体积、更新速度和离线需求决定本地打包或远程加载。
- 无论采用哪种方式，RN 都需要提供加载失败、重试和版本信息展示。

## 实施阶段

### 阶段一：宿主骨架

- [ ] 创建 RN 工程和基础导航。
- [ ] 接入 WebView、加载状态和错误页。
- [ ] 验证 Android/iOS 的前后台切换、返回和横竖屏。

### 阶段二：桥接协议

- [ ] 实现消息封装、请求响应、超时和错误处理。
- [ ] 实现 `app.ready`、`navigation.back`、`network.state` 和存储能力。
- [ ] 在 Web 端加入桥接能力探测和纯 Web 回退。

### 阶段三：游戏流程

- [ ] 从大厅启动游戏并在移动端正确返回。
- [ ] 验证音频、键盘/触摸输入、文件访问和存档。
- [ ] 验证网络游戏和异常断线后的恢复行为。

### 阶段四：真机验证

- [ ] 完成 Android 和 iOS 真机测试。
- [ ] 记录加载速度、内存、耗电和运行时性能问题。
- [ ] 确定需要迁移到 RN 原生实现的模块。

## 验收标准

- RN 应用能够稳定加载现有 Web 游戏大厅。
- 用户能够从大厅启动游戏并正常返回。
- RN/WebView 消息协议有文档、版本号和错误处理约定。
- Android 和 iOS 真机上的横竖屏、音频、网络、存档和生命周期行为符合预期。
- Web 端在没有 RN 宿主时仍可独立运行。
- 关键失败场景提供可理解的错误提示和重试路径。

## 待确认问题

- Web 资源首版采用本地打包、远程加载，还是两者结合。
- RN 工程放在当前 monorepo 的哪个目录，以及采用哪套构建发布流程。
- 移动端是否需要独立的文件和存档目录。
- 是否需要在首版接入账号、推送、分享或支付能力。
