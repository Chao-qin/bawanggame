# 使用会话 ack 与退出判定

## 1. 目标

| 项 | 内容 |
|---|---|
| 目标行为 | 用户直接关闭标签页、浏览器或 App 时，飞书里也能看到这次使用和这一局游戏已经结束，结束时间为最后一次确认的时间 |
| 修改范围 | H5 统计模块（全局心跳、`seq`）、上报协议、服务端会话跟踪与飞书「会话」表、飞书追加写入、上报地址的默认值 |
| 不可破坏 | 原始事件仍按原 19 列追加到「使用统计」「前端报错」「后端日志」；事件去重、离线队列、beacon 规则不变；显式关闭上报时不采集 |
| 验收 | 打开页面立即上报 `app_open`（`seq` 为 1）；页面可见时每 30 秒一次 `heartbeat`；直接关闭页面后约 90 秒，会话行变为「超时结束」 |

## 2. 为什么由服务端判定结束

页面被关闭、浏览器被杀或 App 被划掉时，前端不一定有机会发出最后一个请求。前端只负责持续确认「我还在」，结束由服务端按「多久没收到确认」判定，不依赖退出时的请求。

## 3. 前端（`apps/web/src/analytics.js`）

- 应用是 SPA，统计按一次页面加载（`session_id`）全局进行，与是否在游戏中无关。
- 本次页面加载的每个事件都带 `seq`，从 1 递增。`app_open` 是第一个事件，生成后立即发送；本地有上次离线留下的积压时，本次打开的事件优先发送。
- 页面可见时每 30 秒发一次 `heartbeat`。在游戏中时，心跳附带 `play_id`、`game` 和 `active_ms`；在大厅时只有会话信息。
- 页面隐藏、`pagehide`、APK 切到后台时立即补一条 `heartbeat`，并用 beacon 发出。
- `seq` 只在内存里；事件仍先写入 localStorage 队列，确认送达后删除。

## 4. 服务端（`apps/server/src/reporting/sessions.ts`）

- 每个新收到的事件都确认它所属的会话；带 `play_id` 的使用事件同时确认这一局。
- 会话与每一局各占「会话」表的一行：

| 列 | 说明 |
|---|---|
| 类型 | `应用`（一次页面加载）或 `游玩`（一局游戏） |
| ID | 会话 ID 或游玩 ID |
| 环境 / 设备ID / 平台 / 会话ID | 来自事件 |
| 游戏类型 / 游戏文件 / 游戏名称 | 仅游玩行 |
| 开始时间 | 服务端第一次收到该会话或该局事件的时间 |
| 最后确认时间 | 服务端最后一次收到确认的时间 |
| 最后序号 / 确认次数 | 收到的最大 `seq` 与事件数；同一会话两者相差即为丢失的确认数 |
| 前台时长毫秒 | `active_ms` 累计；「应用」行是本次打开应用内各局游戏的前台时长之和，不含在大厅的时间 |
| 状态 | `进行中` / `已退出`（收到 `game_end`，只用于游玩行） / `超时结束` |
| 结束时间 | 已退出时为 `game_end` 收到时间；超时结束时为最后确认时间 |

- 每 5 秒扫描一次：超过 90 秒（3 次心跳）没有确认的行标为「超时结束」。之后又收到确认（页面只是在后台）时，同一行恢复为「进行中」。
- 新行追加一次，按返回的行号记录；之后按行号覆盖写，多行合并为一次批量请求。状态存于 `LOG_DIR/sessions.json`，服务重启后继续计时、不重复追加。
- 同一工作簿的飞书请求串行发送。

## 5. 一并修复

- 飞书追加：按飞书文档，`insertDataOption` 是查询参数（原先放在请求体里），写入范围需不小于数据（原先是单行 `A1:S1`，改为整列 `A:S`）。此前的接入验证是单行追加且结果正确，生产后端日志表一次启动只留下 1 行与多行追加有关的推断尚未在线上复现，需按第 7 节回读确认。
- 上报地址：`VITE_ANALYTICS_URL` 为空不再表示关闭（发版流程在未设置变量时传入空字符串，导致 APK 与静态站包都不上报），关闭改用 `off`。发版流程未设置 `ANALYTICS_URL` 时默认使用生产地址。

## 6. 已知限制

- 结束时间精度：最多晚于实际离开 30 秒（最后一次心跳之后的部分）；离开时的 beacon 送达时精确到离开时刻。
- 页面在后台超过 90 秒会先记为「超时结束」，回来后恢复为「进行中」；按状态统计时以最终状态为准。
- 离线积压的旧事件在恢复联网后才到达，会以到达时间更新最后确认时间。
- 飞书未返回新行行号时，该行下次变更会再追加一行（重复，不丢失）。
- 会话行按行号原地更新，人工排序、插入或删除行会让后续更新写错行。
- 「最后序号 − 确认次数」只在「应用」行等于丢失的确认数。
- 不在游戏中的心跳只用于确认会话：服务端收到即记去重回执，不进待同步队列、不追加到「使用统计」、不打印到控制台。旧版服务端会拒收这类心跳，须先部署服务端。
