# 虚拟按键与统一输入映射调研

## 目标行为

为后续接入蓝牙手柄、有线手柄、设备实体按键及其他输入设备建立共同的映射入口，使不同来源都能操作当前游戏所支持的虚拟按键，并保留按下、持续按住、松开和连发等行为。

## 修改范围

本文件记录当前 Web/J2ME/MRP 虚拟键盘与输入路径，并提出后续实现边界。本次交付覆盖浏览器键盘、触控和 Gamepad，使用统一逻辑动作层。原生实体按键桥需另行依据平台可捕获能力验证。

## 不可破坏的现有行为

- J2ME 游戏接收 MIDP 键码，短按必须使 press 与 release 被游戏分属不同采样帧观察。
- 多来源按住同一逻辑动作时只发送一次 press，最后一个持有者松开后才发送 release。
- 触控滑动切换方向、方向斜按、长按连发、触觉反馈，以及 blur、隐藏、pagehide 时清理按键状态继续有效。
- MRP 使用其自身的键码和 WASM 事件入口。J2ME 与 MRP 的平台码值不同。
- 既有按游戏保存的 `keymap`、`touchLayout` 设置及默认配置继续可读取。
- 编辑器、设置面板和游戏内对话框等文本输入不能被全局按键映射抢占。

## 验收标准

- 说明触控、键盘、手柄及设备实体按键各自当前的映射路径和覆盖情况。
- 明确共享部分、重复定义、平台差异和映射持久化现状。
- 给出面向多输入源的最小公共模型、接入阶段和风险点。
- 关键现状均能对应到仓库文件和代码位置。

## 现状结论

现有系统共享了触控手势识别与虚拟键盘界面，但还没有统一的输入映射层。`runtime/j2me/touchpad.js` 是 J2ME 和 MRP 共用的触控手势内核，负责 DOM 命中、方向判定、滑动切换、多指去重、连发调度、振动及生命周期释放。它接收调用方提供的 `buttons` 键码表和 `sink.press/release/repeat` 适配器，因此它统一的是触摸操作状态机，不是所有设备到游戏按键的语义映射。

J2ME 目前有三层码值：虚拟键槽位先对应 MIDP 标准动作码，`config.keys` 再按模拟机型转换成游戏所需的机型码，最终通过 `MIDP.sendKeyPress/Release/Repeat` 投递。物理键盘另由 `keymap.js` 的 `keyOf()` 解析，方向、确认、软键、退格、数字及 `*`、`#` 使用固定默认表，用户可按游戏编辑其中九个动作的物理键绑定。

MRP 使用单独的 `KEYCODES`，将相同的虚拟键槽位转成 MR 平台枚举，再通过 `Module._c_event(type, code, 0)` 发送。MRP 物理键盘路径也不同，方向、确认、数字和部分按键交由 SDL，JS 桥只补投 SDL 未覆盖的退格、`*`、`#`。因此若将未来输入设备直接映射到现有平台码，设备绑定会被迫重复维护 J2ME/MRP 两套目标码。

## 映射清单

| 输入来源 | 当前入口 | 当前目标 | 可配置性 |
| --- | --- | --- | --- |
| 屏幕触控，J2ME | DOM 固定槽位 → `Touchpad.bind` → `touchButtons()` → `mapped()` → MIDP 帧同步队列 | 方向、确认、软键、返回、清除、数字、星号、井号的 J2ME/MIDP 码 | 每游戏可配置触摸槽位动作、D-pad 视觉方向、两侧布局、数字排列 |
| 屏幕触控，MRP | 同一 DOM 槽位 → `Touchpad.bind` → `KEYCODES` → `_c_event` | MR 键码 0-23 的子集 | 目前没有发现 MRP 端布局/动作配置接入 |
| 桌面物理键盘，J2ME | `window keydown/keyup` → `keyOf()` → `mapped()` → MIDP 队列 | 方向、确认、软键、返回、清除、数字、`*`、`#` | 每游戏可配置 up/down/left/right/ok/soft1/soft2/clear/back；数字等保持固定 |
| 桌面物理键盘，MRP | document `keydown/keyup` → `PHYS` 或 SDL | MR 键码；SDL 覆盖主要键，JS 补部分码 | 无用户绑定界面 |
| 蓝牙/有线手柄 | 未发现 Gamepad API 轮询、连接事件或控制器适配 | 无 | 无 |
| 设备实体按钮 | 未发现 Android/iOS 原生按键向 WebView 的按键消息协议或专用输入桥 | 无 | 无 |

### J2ME 码值细节

- 触控标准动作码在 `runtime/j2me/keymap.js` 的 `BUTTONS` 中定义，例如方向为 `-1..-4`、确认 `-5`、软键 `-6/-7`、清除 `-8`、返回 `-11`，数字使用 ASCII `48..57`，星号和井号分别为 `42`、`35`。
- `touch-layout.js` 的 `ACTIONS` 是可分配动作，`ACTION_SLOTS` 是可配置槽位。`normalize()` 会补齐默认值并限制未知动作。
- `touchButtons()` 将已配置动作解析成槽位到 MIDP 标准码的表。`mapped()` 再用 `NAMES` 和 `config.keys` 转成当前模拟机型码。
- 物理键盘默认将方向键、Enter、Q/E、Escape、Backspace、数字和 `*`/`#` 解析成标准动作码。`config.keymap` 的自定义匹配只查找 `NAMES` 中的动作，因而当前 UI 项目与可匹配名称是配套的九项。
- `runtime/j2me/config/settings.js` 保存平台预设的机型码。机型码和用户选择的动作码不是同一个概念。
- J2ME 通过 `Settings.setKeymap(gameId, map)` 和 `Settings.setTouchLayout(gameId, layout)` 分开按游戏存储。

### MRP 码值细节

`runtime/mrp/mrp-runtime.js` 的映射为方向 `12..15`、挂机 `16`、软键 `17/18`、确认 `20`、清除 `23`、星号/井号 `10/11`、数字 `0..9`。它与 J2ME 的 MIDP 内部动作编号存在语义对应，但数值不同。触控复用 `Touchpad`，sink 是 MRP 原生事件；重复事件以额外 press 发送，而 J2ME 使用 MIDP repeat。

## 统一性判断

- **统一了**：触控手势算法、固定 DOM 虚拟按键槽位、触控按下/松开边沿、多指持有者去重和主要触控反馈。
- **未统一**：各输入源的设备码解析、动作命名和可编辑绑定；J2ME/MRP 的游戏目标码及事件投递；桌面物理键盘和虚拟触控间的统一状态；跨设备/跨运行时的映射持久化。
- **部分可配置**：J2ME 有按键绑定与触控布局两套独立配置，但目前只对 J2ME 生效；按键绑定限于物理键盘动作，触控布局将固定槽位改指向动作。它不是任意硬件输入到动作的通用配置。
- **生命周期已有基础但不完整统一**：J2ME 帧同步队列、触控持有状态和 MRP 事件投递有不同实现。未来源适配层必须在失焦、断连、切换游戏和播放器卸载时释放其持有的动作，否则容易卡键。

## 建议的目标架构

建议按三个稳定概念组织，而不要把某个设备的原始码直接写入 J2ME 或 MRP 目标码。

1. **输入源适配器**读取一种来源并产生标准化输入标识及边沿。键盘使用 `KeyboardEvent.code`，Gamepad 使用设备标识、按钮索引和轴方向，原生实体按钮由宿主消息传入来源和控制标识。
2. **动作映射**将来源标识映射到运行时无关的游戏动作，例如 `up`、`confirm`、`soft1`、`digit1`、`back`。触控槽位也产出相同动作。按游戏保存用户绑定，保留默认配置的读取兼容。
3. **运行时适配器**将标准动作转换为当前运行时的目标码和事件协议。J2ME 适配器保留机型码转换及帧边沿保证，MRP 适配器保留 MR 键码和 `_c_event` 协议。

动作边沿应带来源/持有者身份。相同动作可同时由多个来源持有，只有第一个持有者生成 press、最后一个释放才生成 release。断连、失焦、页面隐藏及 runtime session teardown 必须释放对应来源全部动作。重复行为由运行时策略控制，不应把 Gamepad 轮询采样频率误当成游戏连发频率。

| 概念 | 示例 | 责任 |
| --- | --- | --- |
| 控件标识 | `keyboard:KeyW`、`gamepad:<device>:button:0`、`native:volume-down` | 输入源适配器 |
| 游戏动作 | `up`、`confirm`、`soft1`、`digit1` | 公共动作映射 |
| 运行时码 | J2ME 标准键码/机型码、MRP 键码 | runtime adapter |
| 动作状态 | 按下、松开、来源持有者集合 | 共用边沿协调器与 runtime adapter |

### 按钮和轴的建议处理

- 蓝牙和有线手柄在浏览器中通常都由 Gamepad API 暴露。第一阶段以连接/断开事件发现设备，并轮询 `navigator.getGamepads()` 读取按键与轴状态。
- 轴映射需配置死区和方向反转，并用不同的按下/释放阈值做滞回，减少中心附近抖动。轴方向转为与按钮完全相同的动作边沿。
- 一个硬件控制可以绑定单个动作；如需组合动作或宏，应作为明确的后续能力，因为它会扩大释放、重映射和配置冲突的复杂度。
- “设备自己的按钮”需按平台确认来源。操作系统保留的音量/电源等按键通常不一定能送到网页或 WebView；Android/iOS 如需支持，应使用原生 key event/按键消息桥，且先明确哪些按键平台允许应用接收。网页侧不能假设能捕获系统级按键。

## 实施阶段建议

1. **先抽动作与平台边界**：从现有 J2ME `BUTTONS`、MRP `KEYCODES` 和两边物理键盘表整理动作枚举及运行时转换；确保虚拟触控和已有键盘仍逐项得到原有结果。
2. **统一键盘和触控配置数据模型**：迁移/归一化现有 `keymap`、`touchLayout` 读取，保留旧数据兼容，并决定设置是每游戏、全局默认后按游戏覆盖，还是二者并存。
3. **加入 Gamepad 输入适配器**：支持多控制器选择、按键捕获、轴死区/滞回、保存与恢复默认、断连释放；UI 可先提供逐游戏映射。
4. **评估原生实体按键桥**：盘点 React Native Android/iOS 可获得的 key events 及被系统拦截的按键，再定义版本化宿主协议。桌面浏览器无需此桥。
5. **完整验证各来源交叉操作**：触控、键盘、两个手柄同时按同一动作，交错释放、轴越阈值、拔出手柄、切后台、runtime 切换及文本编辑焦点；在真实 Android/iOS 设备上独立核实平台实体按键能力。

## 关键风险与待决产品项

- 映射粒度尚未决定：按游戏覆盖、全局默认还是按控制器设备分别保存。建议先采用全局默认加按游戏覆盖，控制器绑定按稳定设备映射信息存储，并在设备标识不可稳定恢复时让用户重新选择。
- 不同浏览器对 Gamepad 设备名称、按钮标准化和轴布局可能不一致，需要显示设备并提供按键捕获流程，不能依赖厂商按钮命名。
- 同一物理键可能同时被浏览器、SDL 或运行时原生层消费。MRP 当前刻意避免对 SDL 已处理按键重复桥接，统一层接入时须按运行时明确键盘事件所有权。
- J2ME 触控短按需要经过 `MIDP.frames` 协调，不能为了抽象统一而改成无条件立即 release；MRP 没有相同帧同步要求。
- WebView 中实体按钮可达性取决于操作系统和宿主实现。无设备/系统级验证时，只能报告协议和模拟器结果，不能宣称实体按钮可用。
- 若需要映射游戏内软键、返回与退出，动作语义要区分“游戏返回键”与“退出播放器”，避免物理返回键改变既有导航行为。

## 代码证据

- `runtime/j2me/touchpad.js`：共享触控状态机、sink 接口、多指去重、连发、滑动及释放清理。
- `runtime/j2me/keymap.js`：J2ME 标准动作码、触控码转换、机型映射、MIDP 帧同步及物理键盘处理。
- `runtime/j2me/touch-layout.js`：触摸槽位、动作白名单、D-pad 视觉布局、数字排序及映射规范化。
- `runtime/j2me/config/settings.js`：机型键码预设以及按游戏保存 `keymap`/`touchLayout`。
- `runtime/j2me/panel.js`：J2ME 物理键盘绑定捕获界面及触控布局/动作配置界面。
- `runtime/mrp/mrp-runtime.js`：MRP 目标键码、SDL/物理键盘补充逻辑、`_c_event` sink 和触控适配。
- `apps/mobile/src/host/protocol.ts`、`apps/mobile/App.tsx`：当前原生消息协议可供后续扩展评估；目前消息含触觉桥，未发现按键输入消息。
