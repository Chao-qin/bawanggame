# Review Matrix

## Passes

每轮按固定顺序执行：`R1` 先做 Diff Review，再做 Feature Audit；只有涉及平台或外部系统时才做 Validation Review。必须完成全部适用的 review pass 并汇总 findings 后才能启动 fixer，不能只完成 Diff Review 就启动。修复后从下一轮重新执行 Diff Review 和 Feature Audit；Validation 仅在原流程需要，或修复触及其覆盖范围时重复。最多 `R3`，不得开启第四轮。

### 1. Diff Review

检查本次 diff 引入的正确性和回归：

- 输入、输出和错误分支是否符合需求。
- 状态更新、异步竞态、重复执行和取消是否正确。
- 生命周期、事件监听器、定时器、全屏、音频和资源是否清理。
- 路由、返回键、WebView bridge 和跨模块调用是否保持契约。
- PR 是否混入无关文件、生成物或其他任务改动。

### 2. Feature Audit

从用户操作开始重建完整流程：

```text
用户动作 -> 路由/状态 -> 副作用 -> 外部资源 -> 成功结果
                                      -> 失败结果 -> 清理
```

检查首次进入、重复进入、返回、退出、刷新、网络失败、权限不足和中断恢复。需要指出是本次改动引入的问题、功能交互问题，还是无法验证的风险。

### 3. Validation Review

涉及平台或外部系统时执行实际验证：

- Web：构建、Node 服务、浏览器冒烟和控制台错误。
- Android：APK 安装、启动、关键 assets、权限和 WebView 请求。
- 网络：权限、API 地址、OPTIONS 预检、CORS、超时和离线提示。
- 性能：设备、持续时间、平均 FPS 或帧间隔、P95、异常帧和长任务。
- 真机：单独记录真实设备型号；模拟器结果不能代替真机结果。

## Severity

- **P0**：数据破坏、无法启动、严重安全问题或所有用户无法完成主流程。
- **P1**：主流程失败、平台发布阻塞、严重回归或资源无法清理。
- **P2**：明确的功能错误、重要平台不兼容或可重复的性能退化。
- **P3**：低风险问题，不阻塞合并，但应记录处理建议。

P0/P1 findings 在完成该轮全部适用 pass 后先触发 fixer；修复后重新 review。若 P0/P1 无法安全修复，必须立即升级并停止交付；若在允许的修复/复审周期后仍存在，则 `blocked` 并停止交付。P2 默认修复，若 `R3` 后仍存在，只有授权负责人通过可追踪 artifact/issue ID 记录风险接受、后续负责人和到期或目标日期才可交付；否则停止交付。P3 可以进入后续任务；无阻塞 finding 时为 `pass`。
